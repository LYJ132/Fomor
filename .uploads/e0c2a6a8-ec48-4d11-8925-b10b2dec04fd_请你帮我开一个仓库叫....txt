一、产品概述

1.1 一句话介绍

一个能够持续理解用户工作与学习过程，并从中发现新技术、新方法和不同解决思路的 AI 探索助手。

它通过分析用户在 Agent 中提出的问题，理解用户正在做什么、想实现什么，以及当前采用的解决方式可能存在什么局限，再主动探索其他可能的解决方案。

它不只是告诉用户有什么新技术，而是帮助用户发现：

面对当前的问题，还有没有另一种值得尝试的解决方式？

1.2 产品定位

这不是一个传统的信息推荐产品，也不是一个每天推送技术新闻的 AI 助手。

它更接近一个持续运行的、以用户为中心的解决方案探索系统。

传统 AI 助手通常遵循这样的工作模式：

用户提出问题 → AI 理解问题 → AI 提供答案。

而本产品希望增加一个新的环节：

用户持续工作与提问 → 系统理解用户正在解决什么 → 识别值得探索的问题 → 主动寻找其他解决方案 → 将有价值的探索结果交给用户。

两者的区别在于：

传统 AI 助手主要帮助用户解决已经意识到的问题；本产品希望进一步帮助用户发现自己尚未考虑过的解决路径。

1.3 核心价值

对用户

1. 拓展认知边界：接触当前工作方式之外的新技术、新方法和新思路。
2. 发现更合适的解决方案：不局限于当前使用的工具和技术栈。
3. 减少重复探索成本：系统持续理解用户的工作背景，不必每次从零开始寻找相关内容。
4. 获得启发而非信息堆积：推荐内容围绕真实问题展开，而不是单纯追逐热点。
5. 建立持续学习的路径：让一次探索能够沉淀为长期有价值的认知和实践。

对产品

产品最重要的竞争力不应该是搜索能力，而应该是：

- 能否从一系列表面问题中理解用户真正想解决的事情；
- 能否识别当前方案之外有价值的探索空间；
- 能否找到与用户实际场景相关的新方案；
- 能否判断这些方案是否真的值得用户了解。

搜索、推荐、记忆和消息推送都是实现这些目标的手段。

二、我们的思考：产品是如何一步步形成的

这一部分保留产品构想中的关键转折。它不仅记录我们考虑过什么，也记录为什么改变方向。

2.1 起点：希望 AI 能够主动带来新的知识与技术

最初的想法是：

能不能做一个 Agent 插件，持续了解用户在日常学习、科研和开发中做了什么，然后主动向用户推荐一些新的技术、工具和知识？

例如：

- 用户正在研究 Agent，系统发现近期出现了值得了解的新型 Agent 架构；
- 用户正在开发数据服务，系统发现一种不同的数据同步方案；
- 用户经常通过 Prompt 调整 Agent 行为，系统发现了一种新的 Agent 控制方式。

这里有一个重要的出发点：

用户日常使用 AI 时，往往只能接触到自己已经知道如何询问的内容。

AI 虽然能够搜索大量信息，但用户需要先知道自己应该搜索什么。

这容易形成一种信息茧房：用户持续围绕熟悉的工具、技术和思路提问，AI 也持续在这些范围内提供答案。

我们希望这个插件能够主动打破这种局限。

2.2 第一次转折：它不是一个每日新闻推送工具

最初很容易把产品理解为一个每天运行的技术资讯推荐器。

例如每天收集用户的兴趣，搜索最新技术新闻，再整理成日报。

但这种方式存在几个问题：

1. 推荐内容容易变成与用户实际工作无关的热点信息。
2. 用户每天不一定都有值得探索的新问题。
3. 技术是否值得了解，不能只由发布时间决定。
4. 新闻、工具和技术介绍并不等于真正能够帮助用户解决问题。

因此，我们逐渐明确：

定时运行只是后台机制，不应该成为产品的核心交互形态。

产品不应该为了每天推送而推送。

如果今天用户没有出现值得探索的问题，系统完全可以什么都不做。

同时，我们对「新」的理解也发生了变化。

新不只是时间上的新技术，还包括认知上的新事物：

- 一项最近出现的新技术；
- 一个用户从未接触过的成熟技术；
- 一种用户当前没有考虑过的工作方式；
- 一种能够改变现有解决路径的技术范式。

因此，产品不应该只关注最新资讯，而应该关注对当前用户而言值得认识的新可能性。

2.3 第二次转折：从推荐知识，转向推荐解决方案

随后我们开始思考：产品最终应该向用户交付什么？

最初考虑的内容包括：

- 新技术；
- 新工具；
- 开源项目；
- 技术文章；
- 论文；
- 工作流；
- 教程。

但这些内容本身并不能直接构成产品价值。

假设用户正在解决一个后台任务管理问题。

仅仅推荐一个新的任务队列工具，用户还需要自己理解它能做什么、为什么需要它、如何接入现有系统，以及它是否真的适合当前场景。

相比之下，如果直接告诉用户：

「你现在使用的 Cron + 脚本适合简单的定时任务，但如果任务开始出现复杂的状态管理、失败恢复和人工介入需求，可以考虑 Task Queue + Worker，或者持久化工作流引擎。」

这才真正形成了一个有价值的探索。

工具只是其中的组成部分。

因此，我们把产品的核心交付对象从 Knowledge 转向 Solution。

一个 Solution 至少应该回答：

- 它解决什么问题？
- 核心思路是什么？
- 它的工作流程是什么？
- 需要哪些技术或工具？
- 相比当前方案有什么不同？
- 有哪些优势和限制？
- 什么情况下值得采用？

这也意味着，产品不能只搜索与用户当前技术栈相似的工具，而要寻找不同的解决方式。

2.4 第三次转折：不再依赖过细的用户意图分类

在设计用户行为分析时，我们曾考虑把用户问题分类。

例如：

- 项目开发；
- 问题排查；
- 技术学习；
- 工具使用；
- 系统部署；
- 工作流优化。

但讨论后发现，这样的分类并不准确。

例如，项目开发和问题排查并不是两种完全独立的活动。用户在项目中调试、解决错误、部署和优化，本来就是项目开发过程的一部分。

如果系统过于依赖这些标签，可能会把一个连续的工作过程切割成很多孤立的问题。

更重要的是，分类本身并不能回答我们真正关心的问题：

用户为什么要做这些事情？他最终想实现什么？当前的工作方式是否存在其他可能？

因此，我们决定不把精细化意图分类作为产品核心。

转而关注一串问题之间的联系。

我们真正需要理解的不是用户每条消息属于什么类别，而是这些消息共同反映了用户正在解决什么问题。

2.5 第四次转折：从单条问题理解，转向 Problem Understanding

这是目前产品逻辑中最重要的一次转折。

用户一天可能会连续提出很多问题。

例如：

- 如何将本地 Docker 数据库迁移到 Supabase？
- 某些复杂的数据采集服务是否应该继续留在本地？
- 本地服务如何连接云端数据库？
- 有没有更方便的工具管理这些本地项目？
- 如何让其他应用访问数据采集服务？
- 数据采集任务失败后应该如何处理？

如果逐条处理，系统可能会分别推荐数据库迁移教程、Docker 管理工具、API 服务框架和任务调度工具。

但这些问题可能都与一个更大的目标有关：

如何构建一套稳定、易维护、能够连接云端与本地服务的数据服务架构？

这意味着系统需要先聚合问题，再理解问题。

我们逐渐形成了一个四层分析模型：

1. Observed Questions：用户实际提出了什么问题？
2. Underlying Goal：用户为什么要解决这些问题？想实现什么？
3. Root Problem：当前阻碍目标实现的核心问题是什么？
4. Solution Space：针对这个问题，还有哪些值得探索的解决方案？

这里需要特别区分：

- 底层目标是用户想实现什么；
- 根本问题是为什么当前的方式无法很好地实现这个目标。

例如：

用户的目标可能是构建稳定的数据服务，而根本问题可能是本地服务与云端基础设施之间的职责边界、部署方式和运行维护机制尚未明确。

当然，系统不能为了得到一个漂亮的分析结论而强行推断根本问题。

当证据不足时，应该保留多个假设，或者明确表示暂时无法判断。

2.6 第五次转折：先判断是否值得探索，再进行搜索

我们还明确了一个重要的工作顺序：

不能先搜索一大堆内容，再从中挑选看起来有价值的内容推荐给用户。

这样做很容易产生信息噪声。

更合理的顺序是：

1. 收集用户一段时间内的问题；
2. 聚合相关问题；
3. 理解用户的目标、现有工作方式和约束；
4. 判断当前问题是否存在值得探索的解决方案空间；
5. 生成具体的探索方向；
6. 再开展搜索；
7. 验证候选方案；
8. 整理为可供用户理解和判断的探索内容。

也就是说，搜索应该由问题驱动，而不是由关键词驱动。

评分的对象也不是单条消息，而是：

用户当前正在面对的问题，是否存在值得探索的其他解决路径？

如果当前方案已经很好，或者不存在明显的探索价值，就不必为了生成内容而强行搜索。

2.7 第六次转折：渐进式理解，而不是一开始就采集所有数据

为了理解用户，系统需要一定的上下文。

但一开始就采集完整会话、读取项目文件、分析整个本地环境，会带来很大的工程和隐私成本。

因此，我们逐渐确定了渐进式采集原则。

第一阶段只记录用户主动发送的问题，不记录 Agent 回复，也不主动扫描本地项目文件。

如果每天的问题已经足够清晰，就直接分析。

如果某个问题缺乏上下文，再利用 session_id 按需读取对应会话历史。

这种方式的好处是：

- 减少数据采集范围；
- 降低存储成本；
- 降低隐私风险；
- 不必一开始就依赖复杂的上下文分析能力；
- 让系统只在真正需要时获取更多信息。

同时，我们明确了一个边界：

这个插件不应该向 Agent 注入指令，也不应该介入 Agent 的正常工作过程。

它是一个独立运行的后台系统，Agent 平台只是提供用户行为数据的入口。

2.8 第七次转折：从短期记录，转向以话题为中心的长期记忆

如果系统每天都在收集问题，那么必然会产生大量没有长期价值的数据。

例如：

- 一次性的报错；
- 临时的语法问题；
- 无关紧要的工具咨询；
- 已经解决且不再需要关注的问题。

这些内容不应该永久保存。

但另一方面，如果用户连续几天都在研究某项技术，或者某个探索结果已经影响了他的项目实践，那么这些内容就值得保留。

因此，我们区分了两种数据：

短期事件记录（Events）

记录用户最近提出的问题，主要用于近期分析。

长期话题记忆（Topics）

记录真正值得持续关注的主题，包括用户的背景、探索进度、反馈和应用情况。

两者不应该混在一起。

原始问题可以过期，但从中沉淀出来的长期话题不应该因为原始数据清理而被删除。

此外，长期记忆也不应该无限增长。

当一个话题长期没有活动时，可以逐步进入休眠、归档，最终过期。

但需要注意：

用户没有反馈，不等于用户不感兴趣。

只有明确拒绝，才应该形成明确的负向偏好。

2.9 当前形成的产品共识

经过以上讨论，我们已经形成了几个比较稳定的判断：

- 产品核心是帮助用户发现新的解决方案，而不是推荐资讯。
- 新颖性既包括时间上的新，也包括用户认知上的新。
- 用户的问题需要聚合和深度理解，不应该依赖过细的意图分类。
- 先理解问题、判断探索价值，再搜索。
- 搜索结果需要经过筛选和验证，不能直接转化为推荐。
- 产品独立于 Agent 会话运行，不注入内容、不干预执行。
- MVP 以用户主动发送的问题为主要数据来源。
- 数据采集遵循渐进式原则。
- 短期事件和长期话题分离。
- MVP 使用 JSON 文件进行存储。
- 后台定时分析是运行机制，不是每日推送的产品目标。

三、问题现状与产品机会

3.1 当前 AI 使用方式的局限

问题一：用户只能围绕已知问题提问

用户需要先意识到某个问题，才能向 AI 提问。

如果用户不知道某种技术、方法或工作流的存在，就很难主动提出相关问题。

AI 可以回答很多问题，但未必能够主动发现用户应该考虑什么。

问题二：AI 容易沿着当前思路继续优化

当用户已经使用某个技术栈时，AI 往往会优先在当前技术栈内寻找答案。

例如用户使用某个数据库，AI 可能会持续提供该数据库的优化方法。

但有时候，真正值得考虑的是换一种架构，甚至改变问题的解决方式。

问题三：日常问题之间的联系容易被忽略

用户的工作和学习具有连续性。

一天内的多个问题可能共同指向一个更大的目标，但单次对话通常只解决其中一个局部问题。

如果没有持续理解能力，AI 很难从这些碎片中发现系统性问题。

问题四：技术资讯与实际问题之间存在距离

很多技术资讯只是介绍新技术的功能和优势。

但用户真正关心的是：

- 它能不能解决我现在的问题？
- 为什么值得了解？
- 和我目前的做法有什么区别？
- 是否需要改变现有架构？
- 引入它的成本有多大？

单纯推荐技术名称并不能满足这些需求。

3.2 产品希望解决的核心问题

本产品希望解决的并不是信息不足，而是：

用户缺乏一种持续发现自身现有解决路径之外的新可能性的机制。

系统需要建立从用户实际行为到解决方案探索的完整链路。

用户行为 → 问题理解 → 探索机会识别 → 解决方案发现 → 方案比较 → 用户反馈 → 长期认知沉淀。

四、产品目标与非目标

4.1 产品目标

目标| 具体说明
持续理解用户| 从日常问题中识别用户正在进行的活动和探索方向
发现潜在问题| 从多个问题中推导用户的底层目标和当前阻碍
识别探索机会| 判断是否存在值得了解的替代、互补或新范式方案
发现新方案| 搜索和验证能够解决实际问题的技术与工作流
建立长期记忆| 通过用户反馈沉淀有价值的话题和探索进度
减少信息噪声| 只展示真正值得用户关注的探索内容

4.2 非目标

MVP 阶段明确不做：

1. 每日技术新闻、论文或资讯日报。
2. 普通 RSS 聚合与关键词订阅。
3. 根据用户兴趣简单推荐工具。
4. 每条用户消息都自动触发一次搜索。
5. 自动优化或修改用户正在运行的 Agent。
6. 向 Agent 会话注入指令、Prompt 或上下文。
7. 默认扫描用户本地项目文件。
8. 替代 Agent 自身的官方文档查询能力。
9. 自动替用户决定是否采用某个技术方案。
10. 一开始就构建复杂的知识图谱或庞大的个人知识库。

官方文档可以在后台作为事实核验和技术证据，但不应成为产品主要推荐内容。

五、核心概念与数据关系

为了避免后续功能设计混乱，需要先明确几个核心对象。

5.1 Event：用户行为事件

Event 是系统采集到的一条原始用户问题。

主要记录：

- 用户发送了什么；
- 什么时候发送；
- 来自哪个 Agent 平台；
- 属于哪个 Session；
- 是否已经参与过分析。

Event 是短期数据，不代表一个长期知识主题。

5.2 Topic：长期话题

Topic 是系统从一系列问题中识别出的、值得持续关注的探索主题。

例如：

- Agent 后台任务管理；
- 本地与云端数据服务架构；
- Agent 执行流程与控制机制；
- 自然语言驱动的数据分析。

一个 Topic 可以关联多个 Event。

一个项目也可以包含多个 Topic，一个 Topic 也可以跨越不同项目。

因此，Topic 不应该简单等同于 Project。

项目可以作为可选的上下文属性，而不是话题的必要归属。

5.3 Problem：待解决的问题

Problem 是系统在理解用户行为后形成的分析对象。

它描述：

- 用户当前正在做什么；
- 想实现什么目标；
- 当前采用什么工作方式；
- 遇到了什么阻碍；
- 有哪些可能的根本问题。

Problem 可以是短期分析结果，也可以在用户持续探索后成为长期 Topic 的一部分。

5.4 Solution：解决方案

Solution 是产品最核心的交付对象。

它不等于工具、技术或开源项目，而是一种完整的解决路径。

建议包含以下信息：

字段| 说明
Name| 方案名称
Core Idea| 核心思路
Workflow| 工作流程
Components| 所需技术、工具和组件
Advantages| 主要优势
Constraints| 限制和代价
Requirements| 前置条件
Applicability| 适用场景
Relationship| 与当前方案及其他方案的关系
Evidence| 支撑该方案的资料和实践证据

5.5 Discovery：一次探索结果

Discovery 是系统围绕某个 Problem 完成一次探索后形成的结果。

它将问题理解、候选方案、证据和方案比较组织在一起，最终交付给用户。

一个 Discovery 可以包含多个 Solution。

一个 Topic 也可以随着时间产生多次 Discovery。

---

六、核心功能设计

6.1 功能一：用户行为采集

目标：以低侵入的方式持续记录用户正在关注的问题。

6.1.1 数据来源

MVP 优先支持具有 Hook 能力的 Agent 平台。

首个适配平台需要支持在用户发送消息后执行 Hook。

6.1.2 Hook 设计

UserMessage Hook

用户每次发送消息后，Hook 在后台执行：

1. 获取用户消息内容；
2. 获取 session_id；
3. 获取时间戳；
4. 获取平台标识及必要元数据；
5. 将事件写入本地队列或事件文件；
6. 结束执行。

Hook 不负责调用大模型、搜索引擎或执行复杂分析。

它的职责只有一个：快速记录用户主动发送的问题。

SessionStart Hook

目前不将 SessionStart Hook 作为必要功能。

此前考虑过在会话开始时向 Agent 注入能力说明，但后来明确不采用这种方式。

产品不应该向 Agent 注入内容，也不应该干预 Agent 会话。

如果未来需要通过 SessionStart 获取平台状态或建立采集连接，必须确保不影响会话内容和 Agent 行为，并单独评估其必要性。

6.1.3 采集字段

建议的 Event 数据：

- event_id
- platform
- session_id
- timestamp
- user_message
- collection_status
- related_topic_id（可选）
- analyzed_at（可选）

不采集：

- Agent 回复；
- 完整会话历史；
- 项目文件；
- 用户本地环境中的其他无关数据。

6.1.4 按需获取会话上下文

如果系统发现某个问题无法独立理解，可以根据 session_id 尝试读取相关会话历史。

例如：

用户说：「那我们还是采用第二种方式吧。」

单独看这条消息没有意义。

此时系统可能需要读取该 Session 中相关的前序消息，理解「第二种方式」具体指什么。

但这项能力依赖平台是否提供历史会话读取接口。

需要进一步确认：

- 是否存在对应 API 或 CLI；
- 能否通过 session_id 获取历史；
- 能否限制读取范围；
- 是否存在数据保留期限；
- 是否需要额外授权。

如果无法获取上下文，系统应保留不确定性，而不是自行补全。

---

6.2 功能二：问题聚合与理解（Problem Understanding）

这是整个产品最核心的分析能力。

目标不是给每条消息打标签，而是从一段时间内的多个问题中，理解用户正在做什么，以及这些问题背后的共同目标。

6.2.1 问题聚合

每天对采集到的问题进行一次集中分析。

系统需要判断：

- 哪些问题属于同一个探索主题；
- 哪些问题只是偶然出现的独立问题；
- 哪些问题可能共同指向一个更深层的目标；
- 是否存在跨项目、跨 Session 的关联。

不能只依赖关键词相似度。

例如：

「如何把 Docker 数据库迁移到 Supabase？」

「本地数据采集服务应该部署在哪里？」

「有没有更方便的本地项目管理工具？」

这些问题表面上属于不同主题，但可能都与数据服务架构的整体设计有关。

反过来，同一个项目中的两个问题也可能完全无关。

因此，聚合时应该综合考虑：

- 问题的语义；
- 目标的一致性；
- 工作流程之间的联系；
- 时间上的连续性；
- 已有 Topic 的历史背景；
- 必要时补充的 Session 上下文。

6.2.2 问题理解模型

建议按照以下结构进行分析。

第一层：Observed Questions

记录用户实际提出的问题。

尽可能保留原始表达，作为后续判断的证据。

第二层：User Activity / Context

理解用户正在做什么。

例如：

- 正在开发一个数据服务；
- 正在搭建 Agent 工作流；
- 正在研究一种新的交互方式；
- 正在优化现有系统。

这一层不要求系统精细分类，而是为了建立问题发生的背景。

第三层：Underlying Goal

理解用户最终想实现什么。

例如：

用户正在迁移数据库，但真正的目标可能是建立一套更容易维护、部署和扩展的数据服务架构。

第四层：Current Approach

还原用户当前采用的解决方式。

包括：

- 使用的工具和技术；
- 当前工作流程；
- 系统的职责划分；
- 已经做出的技术选择；
- 用户尝试过的方案。

第五层：Friction / Constraints

识别当前方式存在的阻碍与约束。

例如：

- 本地与云端服务之间的连接复杂；
- 某些任务需要长期运行；
- 服务部署和维护成本较高；
- 当前技术栈存在兼容性限制。

第六层：Root Problem Hypotheses

尝试推导真正值得解决的问题。

例如：

表面问题是「如何管理本地项目」。

更深层的问题可能是：

「当前的数据服务架构中，哪些职责应该由本地服务承担，哪些应该交给云端基础设施？」

需要强调：Root Problem 应当是一个有证据支持的假设，而不是 AI 为了显得有洞察力而创造出来的宏大问题。

系统应支持：

- 多个竞争性假设；
- 假设的证据来源；
- 置信度；
- 尚未确认的信息；
- 暂时无法判断的情况。

6.2.3 分析结果示例

原始问题：

- 如何迁移 Docker 数据库？
- 哪些复杂的数据采集服务需要留在本地？
- 如何管理本地项目？
- 本地服务如何连接云端数据库？

系统分析：

用户正在做什么？

构建一套由本地数据采集服务和云端数据库组成的数据服务系统。

用户的目标是什么？

希望系统能够稳定运行，同时降低部署和维护成本。

当前采用的方式是什么？

本地运行部分服务，通过接口与其他应用交互，数据库正在考虑迁移至 Supabase。

当前可能存在的阻碍是什么？

本地与云端之间的职责边界、服务部署方式和运行管理机制尚未完全明确。

可能的根本问题是什么？

如何合理划分本地服务与云端基础设施的职责，构建稳定且易维护的数据服务架构？

需要进一步确认什么？

- 哪些服务必须依赖本地环境？
- 数据采集任务是否需要持续运行？
- 是否有实时性要求？
- 是否需要多个应用共享数据？

这一步完成后，系统才真正具备了生成探索方向的基础。

---

6.3 功能三：探索机会识别与评分

目标：判断哪些问题值得进一步探索，而不是对所有问题进行搜索。

6.3.1 评分对象

评分对象不是单条消息，也不是某项技术是否热门。

而是：

用户当前面对的问题，是否存在值得了解的其他解决方案。

6.3.2 评估维度

建议初期从以下维度判断：

维度| 核心问题
解决空间| 当前问题是否存在不同的解决路径？
潜在收益| 新方案是否可能显著改善效率、稳定性或成本？
认知增量| 是否可能让用户接触到此前没有考虑过的思路？
适用性| 新方案是否与用户当前场景存在实际联系？
探索必要性| 用户当前方案是否已经足够好？是否真的需要探索？

可以形成一个综合评分，但不建议一开始就设置过于复杂的评分体系。

更重要的是，系统应该允许判断结果为：

- 值得探索；
- 暂时观察；
- 当前没有明显探索价值。

6.3.3 需要避免的错误

为了新颖而推荐。

新技术不代表更适合用户。

为了推荐而制造问题。

用户当前的方案可能已经足够好，不需要强行寻找替代方案。

过度抽象。

不能仅仅因为用户连续问了几个 Agent 问题，就推断他正在研究某种宏大的 Agent 范式。

重复推荐。

已经探索过且用户明确表示熟悉的内容，不应该反复作为新发现推送。

---

6.4 功能四：解决方案空间探索（Solution Space Exploration）

当某个问题通过探索价值判断后，系统需要从不同角度生成候选方案。

这里的关键不是搜索几个相关工具，而是主动思考：

如果不沿用用户当前的解决方式，还可以怎么做？

6.4.1 四类探索关系

建议将候选方案划分为四种关系。

Alternative：替代方案

用不同的方式解决相同的问题。

例如：

- 当前使用 Cron；
- 替代方案是 Task Queue + Worker。

Complementary：互补方案

在现有方案基础上增加能力。

例如：

- 保留 Cron；
- 增加任务状态管理和失败通知。

Evolutionary：演进方案

当需求规模或复杂度增加时，现有方案可以如何升级。

例如：

- 简单定时任务；
- 任务队列；
- 持久化工作流引擎。

Paradigm Shift：范式变化

从完全不同的角度重新理解问题。

例如：

用户一直在思考如何管理多个定时任务，但也许真正需要的是让任务具备可恢复的执行状态，而不是继续优化调度机制。

6.4.2 候选方案生成

系统应从 Problem Understanding 的结果出发，先生成探索方向，再开展搜索。

例如：

问题：

「如何构建稳定、易维护的后台任务系统？」

可能的探索方向：

1. 优化现有 Cron + 脚本方案；
2. 引入 Task Queue + Worker；
3. 使用持久化工作流引擎；
4. 采用事件驱动架构；
5. 将任务拆分为可恢复的状态机。

这些方案不是互斥的，也不一定只能选一个。

例如，Cron 可以负责触发，Task Queue 负责分发，工作流引擎负责管理复杂执行状态。

系统需要理解方案之间的组合关系。

6.4.3 搜索与证据收集

搜索对象可以包括：

- 新兴技术；
- 成熟但用户不熟悉的技术；
- 开源项目；
- 真实工程实践；
- 技术研究与论文；
- 架构设计案例；
- 社区中的实际使用经验。

搜索时优先围绕具体解决方案展开。

官方文档可以用来核实 API、功能和技术限制，但不应成为最终推荐的主体。

6.4.4 方案验证

对候选方案至少需要验证：

- 技术是否真实存在；
- 是否有可访问的实现或实践；
- 它解决的问题是否与当前 Problem 对应；
- 宣称的优势是否有证据；
- 是否存在重要限制；
- 是否适合用户当前的技术环境。

没有可靠证据的方案不能包装成成熟实践。

6.4.5 方案比较

每个方案都应该说明：

- 核心机制；
- 工作流程；
- 依赖的组件；
- 优势；
- 约束；
- 前置条件；
- 迁移成本；
- 适用场景；
- 与当前方案的关系。

最终不应简单得出「方案 A 比方案 B 好」。

更合理的结论是：

在什么条件下，哪一种方案更值得采用。

---

6.5 功能五：探索结果生成（Discovery）

目标：将复杂的搜索与分析结果，组织成用户能够理解和判断的内容。

产品不应该把搜索结果直接堆给用户。

建议每次 Discovery 包含以下内容。

6.5.1 探索标题

以用户的问题和潜在机会为中心，而不是以某个工具名称为中心。

例如：

「当 Cron 任务开始变复杂，你可能需要的不只是一个调度器。」

6.5.2 我观察到了什么

说明系统为什么会产生这次探索。

引用用户近期提出的相关问题，并说明它们之间的联系。

6.5.3 你真正可能在解决什么问题

呈现系统对用户目标、当前工作方式和潜在根本问题的理解。

如果存在多个假设，应明确展示，而不是只给出一个看似确定的结论。

6.5.4 一个值得了解的新思路

介绍一个可能改变用户思考方式的解决路径。

包括核心机制和工作流程。

6.5.5 其他可选方案

展示替代、互补、演进或范式变化的方案。

不必每次都覆盖全部类型。

6.5.6 与当前方式的区别

重点说明：

- 改变了什么；
- 解决了什么原本难以解决的问题；
- 付出了什么代价；
- 是否值得迁移。

6.5.7 证据与延伸资料

提供相关开源项目、研究、案例和技术资料。

资料应该服务于方案理解和验证，而不是作为内容主体。

6.5.8 后续探索入口

用户可以表达：

- 这个方向很有启发，继续深入；
- 这个我已经了解；
- 暂时不感兴趣；
- 与我当前的场景不相关；
- 我已经尝试过类似方案；
- 我想进一步了解其中某个部分。

用户也可以补充自己的实际情况。

---

6.6 功能六：用户反馈与长期记忆

目标：让系统逐渐了解用户的认知背景和探索进度。

6.6.1 反馈信号

不同反馈代表不同含义，不能简单归为感兴趣或不感兴趣。

用户行为| 系统应该如何理解
明确表示感兴趣| 提高该话题的后续探索优先级
要求继续深入| 延续当前探索
表示已经了解| 更新该话题的知识状态
表示不感兴趣| 记录明确的负向偏好
表示不相关| 修正用户背景或当前问题理解
实际应用某个方案| 记录实践进度和应用结果
没有反馈| 暂时不作判断

特别需要注意：

用户没有反馈，不代表用户不感兴趣。

沉默可能只是没有时间阅读，不能直接作为负向偏好。

6.6.2 Topic 长期记忆

建议每个长期话题包含：

- Topic ID；
- 话题名称；
- 背景和上下文；
- 关联项目（可选）；
- 用户关注的目标；
- 当前探索进度；
- 已经介绍过的方案；
- 用户明确表示了解的内容；
- 用户感兴趣的方向；
- 用户明确排斥的方向；
- 已经实践的内容；
- 相关证据和来源；
- 最后活动时间；
- 生命周期状态。

6.6.3 认知状态需要区分证据强度

不能把 AI 的推测直接当作用户已经掌握的知识。

例如：

- 用户主动说「我之前用过 Temporal」：明确使用过；
- 用户说「我了解 Temporal 的基本原理」：明确表示了解；
- 用户阅读过一次相关探索：仅表示接触过；
- 系统推测用户可能熟悉：低置信度推断。

这些状态需要区别保存。

6.6.4 Topic 生命周期

建议采用：

Active → Dormant → Archived → Expired

- Active：近期持续关注；
- Dormant：一段时间没有新活动；
- Archived：暂时不再主动参与推荐，但仍可恢复；
- Expired：超过保留期限，逐步清理。

具体时间阈值尚未定稿。

初步可以考虑 30 天无活动进入 Dormant、90 天后评估归档，但应支持配置，并根据实际使用情况调整。

全局偏好和话题级偏好也需要分开。

例如用户整体喜欢了解新技术，但明确不想继续研究某个特定技术方向，这两种信息不应互相覆盖。

---

6.7 功能七：后台运行与任务管理

产品不应该依赖用户每次主动调用 Skill。

它应该像一个独立运行的 Agent 扩展服务一样，持续工作。

6.7.1 后台运行机制

主要包括：

- Hook 事件接收；
- 本地事件写入；
- 定时分析；
- 搜索任务调度；
- 探索结果生成；
- 记忆更新；
- 过期数据清理；
- 结果交付。

6.7.2 后台任务状态

建议统一管理任务状态：

Pending → Processing → Completed / Failed

每个任务应具备：

- task_id；
- task_type；
- 创建时间；
- 状态；
- 执行次数；
- 错误信息；
- 关联对象；
- 最后更新时间。

6.7.3 任务可靠性

需要考虑：

- 失败重试；
- 幂等处理；
- 重复事件去重；
- 并发写入保护；
- 原子文件写入；
- 任务中断后的恢复；
- 后台服务重启后的状态恢复。

Hook 本身应该快速结束，不应该因为后台搜索或大模型分析而阻塞用户正常使用 Agent。

---

七、整体业务流程

7.1 日常运行流程

1. 用户在已适配的 Agent 平台中正常工作。
2. UserMessage Hook 记录用户主动发送的问题。
3. 事件写入本地队列或 JSON 文件。
4. 后台服务持续接收和管理事件。
5. 每天在预设时间进行集中分析。
6. 系统聚合问题，理解用户的活动、目标和现有工作方式。
7. 判断是否存在值得探索的解决方案空间。
8. 对有价值的问题生成探索方向。
9. 搜索并验证候选方案。
10. 生成 Discovery。
11. 通过独立 APP 或用户选择的 IM 渠道交付。
12. 用户反馈后，更新长期 Topic。
13. 清理已经过期的原始 Event。

7.2 业务流程图

flowchart TD
    A[用户在 Agent 中正常工作] --> B[UserMessage Hook]
    B --> C[记录用户问题]
    C --> D[本地事件队列 / JSON]
    D --> E[定时分析]
    E --> F[问题聚合]
    F --> G[Problem Understanding]
    G --> H[识别探索机会]
    H --> I{是否值得探索}
    I -->|否| J[暂不生成推荐]
    I -->|是| K[生成探索方向]
    K --> L[搜索与证据收集]
    L --> M[候选方案验证与比较]
    M --> N[生成 Discovery]
    N --> O[APP / IM 交付]
    O --> P[用户反馈]
    P --> Q[更新 Topic 长期记忆]
    Q --> R[短期事件清理]

---

八、产品展示与交互设计

8.1 展示原则

产品不应该将自己变成另一个聊天窗口。

它的主要价值是主动呈现经过理解和筛选的探索结果。

用户不需要每天主动打开它，也不需要阅读一大篇日报。

系统只在出现值得关注的探索内容时进行交付。

8.2 展示形式

目前考虑两种方向。

方案 A：独立 APP 模板

提供一套 APP 模板，由对应 Agent 平台或运行环境生成和展示。

后台服务负责数据与探索逻辑，APP 负责展示和交互。

优势：

- 能够形成完整的探索体验；
- 可以查看历史 Discovery；
- 能够管理 Topic 和长期记忆；
- 不依赖某个具体 IM 平台。

方案 B：IM 渠道交付

用户可以选择通过 IM 接收探索结果。

优势：

- 使用门槛低；
- 不需要额外打开应用；
- 适合轻量提醒和结果摘要。

目前尚未确定最终的交付形态。

建议在架构上将 Delivery Runtime 独立出来，使 APP 和 IM 成为不同的交付渠道。

8.3 建议的 APP 页面结构

以下属于初步交互建议，并非已确认的 MVP 范围。

Discover

展示值得用户关注的探索结果。

内容以 Discovery 为单位，而不是以资讯列表为单位。

Topics

展示正在持续探索的话题。

可以查看：

- 话题背景；
- 历史探索；
- 用户反馈；
- 已了解的内容；
- 当前进度。

History

查看过去生成的探索结果。

Settings

管理：

- 数据采集平台；
- 运行时间；
- 探索偏好；
- 数据保留期限；
- 交付渠道；
- 隐私与数据清理。

九、技术架构与实现原则

9.1 整体架构

产品是独立运行的后台服务，而不是某个 Agent 平台内部的 Skill。

Agent 平台只负责提供用户行为数据。

建议拆分为四个主要部分。

Collection Runtime

负责：

- 平台 Hook 适配；
- 事件接收；
- 事件去重；
- 本地写入；
- 按需读取会话上下文。

Discovery Core

负责：

- 问题聚合；
- Problem Understanding；
- 探索机会评分；
- 候选方案生成；
- 搜索任务生成；
- 方案验证与比较；
- Discovery 生成。

Memory Runtime

负责：

- Event 管理；
- Topic 管理；
- 用户反馈；
- 认知状态更新；
- 记忆生命周期；
- 数据清理。

Delivery Runtime

负责：

- APP 数据接口；
- IM 渠道适配；
- Discovery 推送；
- 用户反馈接收。

9.2 平台适配层

平台适配与核心逻辑必须分离。

例如：

Agent Platform A → Adapter A → Collection Runtime

Agent Platform B → Adapter B → Collection Runtime

核心分析、搜索和记忆逻辑不应该依赖某个 Agent 平台的特定实现。

首期只需要完成一个平台的适配，不必为了未来兼容性提前实现多个平台。

9.3 存储方案

MVP 明确优先使用 JSON 文件。

不需要一开始引入复杂数据库结构，也不需要设计大量关系表和 JOIN。

建议目录结构：

exploration-assistant/
│
├── config/
│   ├── settings.json
│   └── preferences.json
│
├── events/
│   ├── 2026-11-24.json
│   └── 2026-11-25.json
│
├── topics/
│   ├── topic_x.json
│   └── topic_y.json
│
├── discoveries/
│   ├── discovery_x.json
│   └── discovery_y.json
│
├── runtime/
│   ├── scheduler.json
│   └── tasks.json
│
└── logs/

设计原则：

1. 原始 Event 和长期 Topic 分开保存。
2. 每个 Topic、Discovery 使用独立文件。
3. Event 可以通过 topic_id 关联 Topic。
4. 删除 Event 不应该影响 Topic。
5. 使用原子写入，避免文件损坏。
6. 需要考虑文件锁或单写队列，避免并发写入冲突。
7. 重要数据应有备份和恢复机制。
8. 原始问题需要考虑脱敏、权限与保留期限。

JSON 是 MVP 的简化选择，但不意味着可以忽略一致性和数据安全。

9.4 搜索能力

搜索引擎和搜索策略不应该混为一谈。

产品首先需要明确：

- 根据什么问题搜索；
- 如何生成探索方向；
- 需要哪些类型的证据；
- 如何验证候选方案；
- 如何判断方案适用性。

之后再选择具体搜索工具。

优先复用成熟的开源搜索项目或现有搜索服务，采用 Provider 插拔的方式。

不要在 MVP 阶段从零开发搜索引擎。

---

十、数据生命周期与隐私设计

10.1 原始 Event 生命周期

原始问题是短期数据。

目前讨论倾向于保留约 48 小时，以便用户有时间查看探索结果并进行反馈。

MVP 可以只保留最近一至两天的原始问题。

超过保留期限后，删除不再需要的原始事件。

具体清理时机和保留期限需要在实现前确定。

10.2 Topic 生命周期

长期 Topic 需要独立管理。

当一个话题长期没有新活动时，可以逐步降低活跃程度。

但不能简单根据时间判断用户不感兴趣。

用户明确表示不再关注时，可以更新负向偏好；如果只是没有继续互动，则保留为未知状态。

10.3 数据最小化

MVP 阶段：

- 只采集用户主动发送的问题；
- 不采集 Agent 回复；
- 不默认读取完整会话；
- 不扫描本地项目文件；
- 不将所有会话永久保存；
- 只有分析确实需要时，才按需读取有限上下文。

后续可以考虑识别用户是否已经拥有 Memory 工具或插件。

如果存在，可以评估复用其记忆能力；如果不存在，再考虑内置简易记忆系统。

但这不属于 MVP 必须实现的功能。

十一、MVP 范围与版本规划

11.1 MVP：验证核心价值链路

MVP 的目标不是实现一个完整的个人知识管理系统。

而是验证一件事：

能否仅通过用户主动提出的问题，理解用户正在解决的事情，并发现值得用户了解的新解决方案？

MVP 必须实现

1. 数据采集

- 支持一个 Agent 平台；
- 通过 UserMessage Hook 记录用户问题；
- 保存 session_id、时间戳等必要元数据；
- 不影响 Agent 正常工作。

2. 问题分析

- 每日集中分析；
- 聚合相关问题；
- 理解用户当前活动；
- 推导底层目标；
- 还原当前工作方式；
- 识别潜在根本问题；
- 保留不确定性。

3. 探索机会判断

- 先判断是否值得探索；
- 不值得时不生成搜索任务；
- 值得时生成具体探索方向。

4. 方案探索

- 搜索相关技术、开源项目、研究和实践；
- 验证候选方案；
- 生成替代、互补、演进或范式变化的解决方案；
- 比较适用条件与限制。

5. 结果交付

- 生成结构化 Discovery；
- 提供至少一种可用的展示方式；
- 支持用户对探索结果进行反馈。

6. 基础记忆

- 保存长期 Topic；
- 记录用户明确表达的兴趣和认知状态；
- 避免重复推荐已经明确了解的内容；
- 清理过期 Event。

7. 基础运行能力

- 后台定时任务；
- JSON 文件存储；
- 任务状态管理；
- 失败重试；
- 原子写入；
- 基础日志。

MVP 暂不实现

- 多 Agent 平台适配；
- 本地项目文件扫描；
- 自动扫描并复用其他 Memory 系统；
- 完整的知识图谱；
- 复杂的用户画像系统；
- 高度自动化的跨平台推送；
- 用户之间的知识共享；
- 自动修改项目或执行解决方案；
- 复杂的多 Agent 搜索协作。

11.2 后续版本方向

V1.1：提升理解能力

- 更准确的问题聚合；
- 按需读取 Session 上下文；
- 更完善的长期 Topic 管理；
- 更细致的用户反馈机制；
- 解决方案之间的关系管理。

V1.2：提升探索能力

- 多类型搜索 Provider；
- 更丰富的技术与实践资料来源；
- 方案证据验证；
- 方案组合与迁移路径分析；
- 用户认知增量判断。

V2.0：多平台与个性化

- 支持更多 Agent 平台；
- 支持多种交付渠道；
- 可配置探索偏好；
- 更成熟的长期记忆；
- 基于用户反馈调整探索策略；
- 逐步形成个人探索档案。

以上是方向性规划，不代表这些功能都已经完成需求确认。

---

十二、非功能需求

12.1 性能

- Hook 执行应尽可能轻量；
- 不在 Hook 中调用大模型或搜索服务；
- 后台任务不得阻塞用户正常使用 Agent；
- 大模型分析和搜索应在后台执行；
- 单次失败不能导致整个采集流程中断。

12.2 稳定性

- 事件需要避免重复写入；
- 任务支持失败重试；
- 服务重启后能够恢复未完成任务；
- JSON 写入需要具备基本的原子性；
- 多个任务同时执行时需要避免数据冲突。

12.3 可扩展性

- 平台适配层独立；
- 搜索 Provider 可替换；
- 展示渠道可扩展；
- 核心分析逻辑不依赖具体 UI；
- JSON 存储结构应允许未来迁移。

12.4 隐私与安全

- 用户应能够知道系统采集了哪些数据；
- 应提供数据查看和清理能力；
- 默认不采集 Agent 回复；
- 不默认读取本地项目文件；
- 按需读取会话时应控制范围；
- 本地数据应设置合理的访问权限；
- 搜索和外部模型调用前应评估敏感信息脱敏；
- 不应将用户原始问题无差别地发送给外部服务。

十三、产品效果如何衡量

这个产品不能单纯以每日推送数量、搜索结果数量或用户打开次数作为成功标准。

因为推送越多，不代表价值越高。

建议关注以下指标。

13.1 问题理解质量

- 用户是否认可系统对当前目标的理解；
- 用户是否认可系统识别出的当前工作方式；
- 根本问题判断是否具有足够证据；
- 是否频繁出现错误聚合或过度推断。

13.2 探索质量

- 方案是否与用户真实问题相关；
- 是否提供了当前思路之外的新方向；
- 方案是否具有真实的技术或实践依据；
- 是否避免重复推荐；
- 是否能解释不同方案的适用条件。

13.3 用户认知增量

重点关注：

- 用户是否表示第一次了解到某种方法；
- 用户是否因此改变了对问题的理解；
- 用户是否产生了新的探索方向；
- 用户是否开始尝试新的方案；
- 用户是否认为这次探索有启发性。

13.4 长期价值

- 用户是否持续关注某些 Topic；
- 是否形成了连续的探索过程；
- 是否有方案被实际应用；
- 用户是否愿意继续使用系统。

最重要的指标可以概括为：

系统是否帮助用户发现了原本不会主动想到、但对当前问题确实有价值的解决方案。

十四、风险与待解决问题

目前产品的核心方向已经比较清晰，但还有一些重要问题没有讨论完。

14.1 问题理解是否足够准确？

系统仅凭用户主动发送的问题，能否还原用户真实的工作背景？

例如，用户可能省略了大量上下文，或者在不同 Session 中讨论同一个项目。

需要验证：

- 问题聚合是否准确；
- 是否需要更多上下文；
- 如何判断多个问题是否存在因果关系；
- 如何避免过度抽象；
- 如何表达不确定性。

这是产品最重要的风险之一。

14.2 如何定义真正的「新」？

对一个资深开发者而言，某项技术可能早已熟悉。

对另一个用户而言，它可能是全新的。

因此，新颖性不是一个绝对属性，而是与用户认知背景相关。

目前还没有明确讨论：

- 如何建立用户的技术认知画像；
- 如何区分听说过、了解、使用过和熟练掌握；
- 是否需要通过用户主动反馈建立认知档案；
- 如何避免系统仅根据一次提问就判断用户已经掌握某项技术。

14.3 如何生成高质量的候选解决方案？

Problem Understanding 并不自动意味着系统能够找到好的方案。

例如，一个问题可能存在很多理论上的解决方式，但只有少数方案适合用户当前的环境。

需要进一步研究：

- 如何从 Root Problem 推导探索方向；
- 是否需要先让模型生成候选方案，再搜索验证；
- 如何发现跨领域的解决方式；
- 如何避免只搜索与当前技术栈相似的内容；
- 如何评估方案的成熟度和真实可行性。

14.4 如何衡量探索机会？

目前已经确定先评分再搜索，但评分标准还没有定稿。

需要进一步明确：

- 是否使用统一评分；
- 是否设置硬性过滤条件；
- 如何判断当前方案已经足够好；
- 如何判断一个新方案是否真的值得用户投入学习成本；
- 如何处理收益不明显但具有长期认知价值的探索。

14.5 如何选择搜索来源？

目前只明确了搜索能力应当可插拔，并优先复用成熟方案。

但还没有确定：

- 是否需要同时搜索 GitHub、论文、技术社区和技术博客；
- 是否需要 Reddit 等社区经验作为来源；
- 如何判断来源可信度；
- 如何处理不同来源之间的矛盾；
- 如何避免搜索结果被热门项目和营销内容主导。

14.6 交付方式尚未确定

目前考虑独立 APP 模板和 IM 两种方式。

但尚未确定：

- APP 是否属于 MVP；
- 用户是否需要查看历史探索；
- 是否需要主动通知；
- 如何处理同一 Topic 的连续探索；
- 是否需要支持用户手动发起探索。

14.7 用户反馈机制需要验证

反馈是长期记忆的重要来源。

但目前还没有确定：

- 是否需要每条 Discovery 都提供反馈；
- 反馈入口应该有多轻量；
- 用户不反馈时如何处理；
- 如何判断用户真正采用了某个方案；
- 是否需要主动询问用户的实践结果。

14.8 本地运行和部署方式尚未明确

目前已经确定它是独立后台服务，但具体运行环境还需要选型。

例如：

- 是否作为本地常驻进程；
- 是否支持 Docker；
- 如何处理服务开机启动；
- 是否需要远程运行；
- 如何在不同 Agent 平台中安装和管理；
- 如果用户关闭电脑，后台任务如何处理。

十六、下一阶段建议

我不建议现在立刻进入完整的技术选型和开发。

虽然整体架构已经有了初步轮廓，但产品真正的核心能力仍然需要进一步验证。

我认为下一阶段最值得做的是：

优先验证：Problem Understanding → Solution Exploration

可以选取我们已经讨论过的真实问题作为测试样本。

例如：

案例一：本地与云端数据服务架构

输入一系列关于 Docker、Supabase、本地服务、数据采集和项目管理的问题。

验证系统能否：

- 将它们聚合成合理的话题；
- 理解用户真正的目标；
- 识别当前方案的约束；
- 推导出有证据支持的根本问题；
- 发现不同的解决方案。

案例二：Agent 执行效率与工作流

输入一系列关于 Hook、Sub-agent、后台任务、任务分发和工作流的讨论。

验证系统能否从局部问题中识别更高层次的执行机制问题，并发现不同的 Agent 协作方式。

案例三：设计 Agent 的交互方式

输入一系列关于笔、画布、草稿、键盘和鼠标交互的思考。

验证系统能否发现传统办公交互范式之外的设计可能性，而不是简单推荐新的设计软件。

这三个案例能够覆盖技术架构、Agent 工程和交互设计三个不同领域。

如果系统能够在这些案例中产生真正有启发性的探索结果，就说明我们设计的核心逻辑具备初步价值。

十七、产品最终希望成为什么

我们最初想做的是一个能够主动推荐新技术的插件。

但随着讨论深入，产品的定位逐渐发生了变化。

它不再只是一个技术推荐器，也不只是一个能够记住用户兴趣的 AI 助手。

它希望成为一个持续理解用户、拓展用户认知边界的探索系统。

用户不必每天告诉它自己想学习什么，也不必提前知道应该搜索什么。

它通过用户日常的工作和提问，逐渐理解用户正在做的事情，并在合适的时候提出新的可能性。

它不替用户决定，也不强行改变用户当前的工作方式。

它只是帮助用户看到：

除了现在这条路，你可能还有其他值得尝试的路。

这就是这个产品希望创造的价值。
