# Fomor

Fomor 采集用户在 Trae 中提出的问题，每天由自动化任务中的 **Agent（你）** 按本文档执行一次探索，产出当天的探索结果（个人助理开场 + 探索目录 + 具体内容 + 结尾）。所有机械步骤（收集、清理、状态提交）都由 `scripts/fomor` 完成，你只负责理解、思考、搜索与写作。

职责划分：

| 组件 | 触发时机 | 做什么 |
| --- | --- | --- |
| `UserPromptSubmit` Hook（`scripts/fomor hook`） | 用户发消息 | 静默把问题追加到 `~/.fomor/events/`，不阻塞、不注入、不分析 |
| `SessionStart` Hook（`scripts/fomor session-start`） | 会话开始 | 静默创建/校验 `~/.fomor/`，不输出 |
| `scripts/fomor prepare / finish` | 每日探索前后 | 代码完成：读取事件与快照；成功后清理本轮已读事件 |
| `scripts/fomor dislike` | **仅用户主动调用 Skill 时** | 记录用户明确拒绝的内容 |
| **自动化任务** | 每天定时 | 你按本文档「每日探索 SOP」执行 |
| 本技能 | 用户调用 / 自动化任务 | 部署与管理（A）；每日探索 SOP（B）；主动调用（C） |

三条硬性边界，任何时候都不违反：

1. **事件无处理标记**：不添加 processed/analyzed 字段；事件文件只在分析成功后由 `finish` 按快照清理。
2. **分析失败不清理**：中断、搜索失败、结果生成失败都不调用 `finish`，原始事件完整保留，下次重新分析。
3. **Disliked 只进不出、只在主动调用时更新**：每日自动化任务只读不写；用户沉默、没追问、没点击都不是拒绝，不得推断。

## A. 部署与管理（用户说「安装/检查 Fomor」时）

**命令路径约定**：下文 `scripts/fomor` 指 Fomor 仓库（或插件）根目录下的脚本。不在仓库根目录时用绝对路径（如 `~/fomor/scripts/fomor`）；Windows 把 `python3` 换成 `python`。

动手前先问用户两件事：

1. **安装范围**：全局（所有工作区可用，推荐）还是只装当前项目？
2. **是否已有 Hook 配置**：已有 `hooks.json` 时必须合并，不能覆盖。

同时说明：部署中有几件事**只能由人完成**——启用 Hook（含安全确认）、信任工作区、必要时手动粘贴配置。除这些之外由你执行，不要声称用户已完成。

### A1. 环境检查

```bash
scripts/fomor session-start --verbose
```

- 输出含 `"ok": true` 即数据目录就绪（`~/.fomor` 会自动创建，不要手动改里面的文件）；
- 命令报错或提示缺少 python：请用户安装 Python 3.10+ 后重试，不要继续后续步骤。

### A2. 安装 / 更新 Skill

如果你能读到本文档，说明 Skill 已加载；若是首次安装，把仓库的 `skills/SKILL.md` 放到下面任一位置：

| 范围 | 路径 |
| --- | --- |
| 全局（国内版） | `~/.trae-cn/skills/fomor/SKILL.md` |
| 全局（国际版） | `~/.trae/skills/fomor/SKILL.md` |
| 项目级 | `<项目>/.trae/skills/fomor/SKILL.md` |

Windows 把 `~` 换成 `%USERPROFILE%`。

### A3. 配置采集 Hook

把仓库 `hooks/hooks.json` 里的 `${TRAE_PLUGIN_ROOT}` 替换为仓库绝对路径，合并到对应文件：

| 范围 | 文件 |
| --- | --- |
| 全局（国内版） | `~/.trae-cn/hooks.json` |
| 全局（国际版） | `~/.trae/hooks.json` |
| 项目级 | `<项目>/.trae/hooks.json` |

需要的两条命令：

```text
UserPromptSubmit → <仓库绝对路径>/scripts/fomor hook
SessionStart     → <仓库绝对路径>/scripts/fomor session-start
```

- **合并而不是覆盖**：保留用户已有的其他 Hook；
- **写不进去就交给用户**：如果无法直接修改该文件，把完整 JSON 输出给用户手动粘贴，并明确说明「这一步尚未完成」；
- **必须由用户完成的三件事**（逐条提醒）：
  1. 在 Trae「设置 > Hooks」启用这两条 Hook；
  2. 信任当前工作区（项目级 Hook 需要）；
  3. 允许「本地自动运行」——Hook 要写 `~/.fomor/`，安全提示由用户点击确认；
- 即使 SessionStart 未启用，首次 `hook` 也会自动创建数据目录，不会丢消息。

### A4. 由你创建自动化任务

不要让用户手动新建。使用 Trae 的对话创建能力，按以下模板创建（`<时间>` 取 `scripts/fomor status` 输出的 `schedule` 值）：

```text
任务名称：Fomor 每日探索
触发：每天 <时间>
任务内容：
使用 fomor 技能执行今日探索：
1. 阅读 fomor 技能中的「每日探索 SOP」，按 Step 0 到 Step 6 完整执行；
2. 若结论是没有值得探索的方向，明确说明并只执行 Step 6 提交，不生成低质量内容；
3. 否则把今天的探索结果完整展示给我，并告诉我它保存在哪里；
4. 遇到报错或数据不足时如实说明，不要编造。
```

创建后告知用户：任务创建后运行环境不可修改；本地任务睡眠期不执行，错过的探索会在下次运行时补上（未分析的事件会一直保留）。若对话创建无法指定「本地」运行环境，明确告知：云端任务读不到 `~/.fomor/`，需删除后在「自动化」界面手动重建为本地。

### A5. 自检

```bash
printf '%s' '{"session_id":"setup-check","prompt":"Fomor 安装自检","hook_event_name":"UserPromptSubmit"}' | scripts/fomor hook
scripts/fomor status
```

`events` 增加 1、重复执行不再增加即采集正常。从 `~/.fomor/events/<当天>.jsonl` 删除 `session_id` 为 `setup-check` 的那一行（只删这一行）。

### A6. 收尾报告

向用户逐项说明：

- 仓库路径、Python 版本；
- Skill 安装位置；
- Hook 配置文件位置，以及是否已由用户在设置中启用；
- 自动化任务名与触发时间；
- **仍需用户手动完成的项**（没有就写「无」）。

任何一步失败都要如实说明并给出排查方向，不要为了交付而假装成功。

## B. 每日探索 SOP（自动化任务 / 用户主动要求分析时执行）

执行顺序：Step 0（取数据）→ Step 1 观察 → Step 2 假设 → Step 3 发现新可能性 → Step 4 研究与评估 → Step 5 输出 → Step 6 提交。

四个分析阶段是自然的推导关系，不是逐条填写的问卷：每个阶段只选适用的核心问题来思考，综合得出结论后再进入下一阶段；如果后面的推理发现前面的理解明显不成立，可以回到前面修正，但不需要额外的证据等级、置信度评分或校验流程。

写任何结论时都要区分「用户明确说过的」和「你推断出来的」：推断要标成推断，不要写成用户已经确认的需求。

### Step 0：Prepare（唯一数据入口）

```bash
scripts/fomor prepare
```

输出 JSON：`events`（所有尚未成功分析的用户消息）、`dislikes`（用户明确拒绝的内容）、`snapshot`（本轮读取边界）。**不要自己删文件、不要改 runtime state、不要读历史报告**——事件文件在 `finish` 之前保持原样。

### Step 1：Observation（观察用户活动）

目标：建立对用户当天工作的整体理解，找出值得继续关注的现象。**本阶段只描述看到了什么，不解释原因，也不提前提方案。**

1. 他今天主要在推进什么任务？把提问按「同一件事」归组，而不是一条条孤立地看。
2. 哪些行为、问题或决策值得注意——重复提问、反复修正、任务卡住、绕远路、临时改主意？
3. 这些活动之间有时间或目标上的联系吗？几条看似不同的问题，是否指向同一件还没说出口的事？
4. 哪些现象可能说明他有某种还没被满足的需求？（这里只记录现象，不急着解释）

看到什么就写什么，不要在这一步判断好坏，也不要急着解释。记录时标明哪些是他的原话、哪些是你的推断。

### Step 2：Hypothesis（挖掘潜在需求）

目标：理解他真正想完成什么，并推导他可能缺少的知识、方法、工具和经验。**Fomor 深入的是对需求的理解，不是把少数搜索结果研究得更深。**

1. 他真正想完成的是什么？为了达到这个目标，需要具备哪些知识、方法、工具和条件？
2. 对照这些条件，他现在可能缺少什么？既包括他明确表达过的困难，也包括从他的活动里能合理推导出、但他还没意识到的需求。
3. 他当前的解决方式有哪些局限？这些局限更可能来自认知、方法、工具、流程，还是协作？
4. 遇到重复强调、反复修正或多次尝试时，问题更可能出在哪一环——需求表达、Agent 理解、执行能力还是协作方式？不要简单归因于「用户不会写 Prompt」。

例：他今天主要在改个人网页 UI。不要只总结「改了哪些页面」，而应想到他可能缺：视觉风格的认知、描述动效的专业术语、优秀案例与组件资源、提升审美的方法、组织页面信息的设计方法。

六种缺口维度（知识 / 方法 / 工具 / 工作流 / 方案 / 视野）只是提醒自己别漏方向的提示，不必逐项检查，也不要变成固定分类。

推导出的需求要标明是推断，不要写成他已经确认的需求。

### Step 3：Opportunity Discovery（广泛发现新可能性）

目标：从潜在需求出发，先打开探索空间，而不是过早挑一个方向往下钻。

1. 围绕他的潜在需求，从知识、方法、工具与资源、实践案例、工作流、跨领域思路等不同角度，分别能想到哪些可能性？
2. 哪些是他很可能不知道、但和目标相关的——专业概念、设计语言、成熟实践、新方法？
3. 有没有超出他当前工具和技术栈、甚至来自其他行业的做法？
4. 这些可能性分别满足他哪部分需求？（不必都指向同一个问题，允许多个方向并行）

不要过早收敛到一个方案，也不要只找与现有做法高度相似的替代品。跳过 `dislikes` 里明确拒绝的内容。方向可以多，但每个都要是他可能真正用得上、而他原本不知道的东西。

### Step 4：Research & Evaluation（筛选与验证）

目标：广泛探索之后守住质量——确保留下的东西真实、相关、有新意、值得看。

1. 它真实存在吗？有可靠来源或可访问的资源吗？
2. 它和用户的实际工作或潜在需求相关吗？
3. 它带来了新的知识、方法、资源或思路吗？还是只是换了说法的重复？
4. 它值得占用他的注意力吗？与其他发现是否重复？

搜索与验证要服务于多个方向，不要把某一个方向研究得很深却忽略其他同样有价值的发现。默认不做长篇深度研究；只有需要讲清一个概念、判断方案是否真实可用、或比较适用条件时才深入。查不到可靠来源就不放进来，不要编造。

### Step 5：Output（今日探索结果）

输出一份当天的探索结果，直接展示在对话里，同时写入 `~/.fomor/reports/<YYYY-MM-DD>.md`。结构固定四部分：**个人助理开场 → 今日探索目录 → 分类展开的具体内容 → 简短结尾**。目录必须先于具体内容。

**1. 开场**：两三句，用自然口吻说明今天看到他在做什么、准备了哪些可能有用的新内容。不要写成日报总结，也不要复述分析过程。

**2. 今日探索目录**：按主题或内容类型分组，每条直接给出具体的知识、方法、工具或资源，并附一句说明。**目录里不要出现「如何提升审美」「有哪些好工具」这类问题**——目录本身就要有信息量，只看目录也能拿走东西。

```markdown
## 今日探索目录

### 01 · 值得尝试的视觉风格
- **新粗野主义（Neo-Brutalism）** — 大胆的边框、强烈的色彩和直接的视觉表达。
- **像素风格（Pixel Art）** — 用像素语言创造独特的视觉识别。

### 02 · 值得认识的 UI 动效语言
- **Parallax Scrolling** — 视差滚动。
- **Shimmer Effect** — 流光扫过。
```

（以上仅示意形态；实际分组与条目必须来自当天分析，不要套用。）

**3. 具体内容**：目录之后按类型灵活展开。可以参考下面骨架，但不必每个条目都用同一套字段：

```markdown
## 01. <具体知识 / 方法 / 工具名称>

它是什么，核心特点。

**为什么值得了解**：结合他当前在做的事，说明能满足什么需求或打开什么思路。

**可以怎么应用**：给出具体的使用场景或建议。

**继续探索**：相关网站、案例、教程或项目链接。
```

不同类型的侧重可以不同：概念讲定义与原理；风格讲视觉特征与代表作；方法讲思路与适用场景；工具讲用途、特点与链接；案例讲它解决了什么、值得借鉴什么；技术/工作流讲机制与可借鉴之处。每个条目讲清「是什么、为什么对他有用、下一步去哪看」即可，不写成长篇教程。

**4. 结尾**：一两句自然收尾，不布置任务，也不强迫他选择某个方向。

没有任何值得展示的发现时，不生成文件，在对话里说明「今天没有发现值得分享的新内容」即可。

### Step 6：Finish（成功后提交）

**只有完整分析成功完成后**才执行。把 Step 0 的 `snapshot` 原样传回：

```bash
printf '%s' '{"snapshot":{...Step 0 的 snapshot 原文...}}' | scripts/fomor finish
```

`finish` 会只删除本轮已读取的事件（分析期间新增的消息会保留到下一轮）。失败时（`finish` 报错）不要重试删除，如实报告即可——事件会留在磁盘上，下次重新分析。

每日自动化任务在 Step 0→6 全程：**不更新 Disliked、不读取 pending、不做反馈回看、不要求用户确认是否感兴趣**。

## C. 用户主动调用（唯一允许更新 Disliked 的入口）

用户主动调用 Fomor Skill 时可以：

- **手动执行一次探索**：按 B 部分 Step 0→6 执行；
- **查看/讨论结果**：读 `~/.fomor/reports/` 下当天的探索结果，展开讨论；
- **更新 Disliked**：仅当用户**明确表达拒绝**时执行：

```bash
scripts/fomor dislike --name "<内容名称>" [--category content_preference]
```

Disliked 更新规则：

1. 只记录用户明确说「不想再看到这类内容」的条目；
2. 用户只是调用了 Skill 但没表达拒绝 → **不更新**；
3. 用户沉默、没点击、没追问、没用某个方案 → **不推断为拒绝**；
4. 重复条目自动去重，不需要反馈状态或时间线。

## 数据与配置速查

```text
~/.fomor/
├── config.json               {"timezone": "Asia/Shanghai", "schedule": "03:00"}
├── events/YYYY-MM-DD.jsonl   用户问题，无处理标记；finish 按快照清理已分析的
├── profile.json              {"version": 1, "dislikes": [...]} 只记明确拒绝
├── reports/                  当天的探索结果（留存，可随时删除，不参与每日分析）
└── runtime/state.json        {"last_successful_analysis_at"}
```

Event 只有 5 个字段：`event_id`、`session_id`、`timestamp`、`user_message`、`fingerprint`。

常用命令：`scripts/fomor status`（概览）、`cat ~/.fomor/reports/*.md`（查看结果）。
