# Fomor

Fomor 采集用户在 Trae 中提出的问题，每天由自动化任务中的 **Agent（你）** 按本文档执行一次探索：先采集问题与必要上下文，再分析用户在做什么，然后按已安装的 Pack 做专项探索，最后产出当天的探索结果。所有机械步骤（收集、清理、状态提交）都由 `scripts/fomor` 完成，你只负责理解、思考、搜索与写作。

职责划分：

| 组件 | 触发时机 | 做什么 |
| --- | --- | --- |
| `UserPromptSubmit` Hook（`scripts/fomor hook`） | 用户发消息 | 静默把问题追加到 `~/.fomor/events/`，不阻塞、不注入、不分析 |
| `SessionStart` Hook（`scripts/fomor session-start`） | 会话开始 | 静默创建/校验 `~/.fomor/`，不输出 |
| `scripts/fomor prepare / finish` | 每日探索前后 | 代码完成：读取事件与快照；成功后清理本轮已读事件 |
| `scripts/fomor dislike` | **仅用户主动调用 Skill 时** | 记录用户明确拒绝的内容 |
| **自动化任务** | 每天定时 | 你按本文档「每日探索 SOP」执行 |
| 本技能 | 用户调用 / 自动化任务 | 部署与管理（A）；每日探索 SOP（B）；主动调用（C） |
| `packs/*.md` | Step 1 匹配、Step 2 探索 | 领域专属的观察方向、判断规则、探索方法与筛选标准 |

三条硬性边界，任何时候都不违反：

1. **事件无处理标记**：不添加 processed/analyzed 字段；事件文件只在分析成功后由 `finish` 按快照清理。
2. **分析失败不清理**：中断、搜索失败、结果生成失败都不调用 `finish`，原始事件完整保留，下次重新分析。
3. **Disliked 只进不出、只在主动调用时更新**：每日自动化任务只读不写；用户沉默、没追问、没点击都不是拒绝，不得推断。
4. **每日任务不创建、不修改 Pack**：Pack 由用户与团队维护；自动化任务只在报告里给出建议。

## A. 部署与管理（用户说「安装/检查 Fomor」时）

**命令路径约定**：下文 `scripts/fomor` 指 Fomor 仓库（或插件）根目录下的脚本。不在仓库根目录时用绝对路径（如 `~/fomor/scripts/fomor`）；Windows 把 `python3` 换成 `python`。

动手前先问用户两件事：

1. **安装范围**：全局（所有工作区可用，推荐）还是只装当前项目？
2. **是否已有 Hook 配置**：已有 `hooks.json` 时必须合并，不能覆盖。

同时说明：部署中有几件事**只能由人完成**——启用 Hook（含安全确认）、信任工作区、必要时手动粘贴配置。除这些之外由你执行，不要声称用户已完成。

### A1. 环境检查

```bash
scripts/fomor session-start --verbose
```

- 输出含 `"ok": true` 即数据目录就绪（`~/.fomor` 会自动创建，不要手动改里面的文件）；
- 命令报错或提示缺少 python：请用户安装 Python 3.10+ 后重试，不要继续后续步骤。

### A2. 安装 / 更新 Skill

如果你能读到本文档，说明 Skill 已加载；若是首次安装，把仓库的 `skills/fomor/SKILL.md` 放到下面任一位置：

| 范围 | 路径 |
| --- | --- |
| 全局（国内版） | `~/.trae-cn/skills/fomor/SKILL.md` |
| 全局（国际版） | `~/.trae/skills/fomor/SKILL.md` |
| 项目级 | `<项目>/.trae/skills/fomor/SKILL.md` |

Windows 把 `~` 换成 `%USERPROFILE%`。

### A3. 配置采集 Hook

把仓库 `hooks/hooks.json` 里的 `${TRAE_PLUGIN_ROOT}` 替换为仓库绝对路径，合并到对应文件：

| 范围 | 文件 |
| --- | --- |
| 全局（国内版） | `~/.trae-cn/hooks.json` |
| 全局（国际版） | `~/.trae/hooks.json` |
| 项目级 | `<项目>/.trae/hooks.json` |

需要的两条命令：

```text
UserPromptSubmit → <仓库绝对路径>/scripts/fomor hook
SessionStart     → <仓库绝对路径>/scripts/fomor session-start
```

- **合并而不是覆盖**：保留用户已有的其他 Hook；
- **写不进去就交给用户**：如果无法直接修改该文件，把完整 JSON 输出给用户手动粘贴，并明确说明「这一步尚未完成」；
- **必须由用户完成的三件事**（逐条提醒）：
  1. 在 Trae「设置 > Hooks」启用这两条 Hook；
  2. 信任当前工作区（项目级 Hook 需要）；
  3. 允许「本地自动运行」——Hook 要写 `~/.fomor/`，安全提示由用户点击确认；
- 即使 SessionStart 未启用，首次 `hook` 也会自动创建数据目录，不会丢消息。

### A4. 由你创建自动化任务

不要让用户手动新建。使用 Trae 的对话创建能力，按以下模板创建（`<时间>` 取 `scripts/fomor status` 输出的 `schedule` 值）：

```text
任务名称：Fomor 每日探索
触发：每天 <时间>
任务内容：
使用 fomor 技能执行今日探索：
1. 阅读 fomor 技能中的「每日探索 SOP」，按 Step 0 到 Step 3 完整执行；
2. Pack 安装与匹配情况是报告必写部分，即使本次没有发现也要展示；
3. 若没有值得探索的新内容，如实在报告中说明，不生成低质量内容，然后照常提交 finish；
4. 遇到报错或数据不足时如实说明，不要编造。
```

创建后告知用户：任务创建后运行环境不可修改；本地任务睡眠期不执行，错过的探索会在下次运行时补上（未分析的事件会一直保留）。若对话创建无法指定「本地」运行环境，明确告知：云端任务读不到 `~/.fomor/`，需删除后在「自动化」界面手动重建为本地。

### A5. 自检

```bash
printf '%s' '{"session_id":"setup-check","prompt":"Fomor 安装自检","hook_event_name":"UserPromptSubmit"}' | scripts/fomor hook
scripts/fomor status
```

`events` 增加 1、重复执行不再增加即采集正常。从 `~/.fomor/events/<当天>.jsonl` 删除 `session_id` 为 `setup-check` 的那一行（只删这一行）。

### A6. 收尾报告

向用户逐项说明：

- 仓库路径、Python 版本；
- Skill 安装位置；
- Hook 配置文件位置，以及是否已由用户在设置中启用；
- 自动化任务名与触发时间；
- **仍需用户手动完成的项**（没有就写「无」）。

任何一步失败都要如实说明并给出排查方向，不要为了交付而假装成功。

## B. 每日探索 SOP（自动化任务 / 用户主动要求分析时执行）

执行顺序：**Step 0 采集 → Step 1 分析 → Step 2 专项探索 → Step 3 输出**。

全局规则：

- 四个阶段是自然的推导关系，不是逐条填写的问卷：只选适用的引导问题来思考，综合得出结论后再进入下一阶段；后面发现前面的理解不成立时，可以回去修正。
- 写任何结论都要区分「用户明确说过的」和「你推断出来的」：推断标成推断，不写成用户已确认的需求。
- 分析失败（中断、报错、报告没写完）不执行 `finish`，原始事件完整保留，下次重新分析。
- 全程只读 `dislikes`，不更新；不做反馈回看，不要求用户确认是否感兴趣。

### Step 0：采集（Collection）

目标：收集用户提出的问题，以及理解这些问题所需的上下文。**不在这一阶段做深入探索。**

#### 0.1 读取已采集的用户提问

```bash
scripts/fomor prepare
```

实际存储位置与格式（已按当前代码核实，直接使用，不要凭空猜测）：

- 文件：`~/.fomor/events/YYYY-MM-DD.jsonl`，每天一个文件，每行一个 JSON 对象（UTF-8，JSONL）；
- Event 共 5 个字段：`event_id`、`session_id`、`timestamp`（ISO 8601）、`user_message`（用户提问原文）、`fingerprint`（`trae|session_id|规范化消息` 的 sha256，采集去重用，分析时忽略）；
- `prepare` 输出 JSON：`events`（全部未清理事件，按时间排序）、`dislikes`（用户明确拒绝的内容）、`snapshot`（本轮读取边界，逐文件行数）；
- **snapshot 必须原样保留**，Step 3 报告完成后传给 `finish`；`prepare` 只读不删、不打任何处理标记。不要自己删事件文件、不要改 runtime state、不要读历史报告做分析输入。

#### 0.2 判断是否需要获取上下文

先通读 `events`，初步观察是否存在值得进一步了解的地方：

- 表达模糊、不准确，或**反复尝试描述同一个东西**（反复描述、反复修正往往是重要线索，不是用户偏好）；
- 解决问题时表现出对某些概念、技术或方法的不熟悉；
- 正在做某项设计、开发或技术决策，但消息本身说不清背后的原因；
- 提出的问题可能只是某个更深层问题的表面表现。

消息已足够理解行为与意图 → 不获取额外上下文。只围绕值得探索的线索获取，不无条件拉取全部历史。

#### 0.3 获取相关上下文（平台会话读取，2026-11-28 本机实测写定）

以下说明基于对 Trae CN（Windows）本机数据的实测验证，直接按步骤执行，**不需要重新调研平台规则**：

背景事实（已实测确认）：

- 会话原始对话（用户/Agent 消息原文）**不可读**：存储在 `%APPDATA%\Trae CN\ModularData\ai-agent\database.db`（文件头非 SQLite，已加密），且无公开 API；
- Fomor events 里的 `session_id` 就是会话 ID，与 memory、snapshot、attachments 中的同名 ID 一致；
- 可读的上下文来源是 **Trae 自己的 memory 目录**，明文、按 session_id 组织。

读取步骤：

1. **消息级摘要（首选）**：
   - 文件：`~/.trae-cn/memory/projects/*/YYYYMMDD/session_memory_<session_id>.jsonl`（国际版 `~/.trae/memory/...`）；
   - 定位方式：跨项目目录按文件名通配 `session_memory_<session_id>.jsonl`，不要从工作区路径推导目录名；
   - 每行一个 JSON，代表一次交互回合，字段：
     - `intent` — 该回合用户想做什么；
     - `actions` — Agent 做了哪些动作（列表）；
     - `outcome` — 结果与状态；
     - `learned` — 过程中确认的知识点（列表）；
     - `message_summary_time` — 时间。
   - 按时间顺序读取与当前线索相关的回合，即得到该会话的「用户意图 + Agent 已提供内容」——正好支撑 Step 1 的分析。
2. **主题级摘要（补充）**：同目录的 `topics.md`，段落以 `[session_id: ... | topic_summary_time: ...]` 开头，是该会话的整体摘要。
3. **项目级背景**：`~/.trae-cn/memory/projects/<工作区目录>/project_memory.md`，了解用户的项目约定与历史决策。
4. **局限（都要记住）**：
   - memory 只有 Trae 写过摘要的会话才有文件——找不到就是没有，不要猜；
   - 摘要不含用户消息原文（原文用 events 的 `user_message`）；
   - 会话结束后摘要可能有几分钟延迟才落盘。

降级处理：memory 文件不存在或解析失败 → **上下文不可用**：只用 `events` 的问题原文继续，报告中把依赖上下文的结论标为「基于有限信息」。**绝不编造对话内容**。

其他可读信号（可选，价值有限，不要花太多时间）：`%APPDATA%\Trae CN\ModularData\ai-agent\inbox\<target_session_id>\next\messages.jsonl`（跨会话消息的摘要与时间戳，无正文）；`command-execution\<executionId>\execution.json`（命令执行的 cwd 与时间，与会话 ID 的对应关系未确认）；`User\globalStorage\state.vscdb`（标准 SQLite，只读）中的 `chat-suggest:cache:<session_id>` 键（含 `messagesLength` 会话消息数与 `savedAt` 时间戳，可粗判会话规模）。

Step 0 产出：一组「用户提问 + 必要上下文」的采集结果——events 原文、memory 中按线索摘取的 intent/learned 片段、每条线索的来源 `session_id`。

### Step 1：分析（Analysis）

只建立整体认知，不开展专业领域的深入探索。

1. **用户当前在做什么？** 把问题按项目/任务归组；一个用户可能同时推进多个项目，尽量区分，并把相关问题归属到对应项目。
2. **Agent 已经提供了什么？** 整理相关对话中 Agent 已经给出的内容——已解释的专业概念、已推荐的工具/技术/方案、已讨论的设计思路与替代方案。这是后续判重基线。注意：**Agent 提到过 ≠ 用户已掌握**，后续仍要判断是否存在未解决的认知缺口。
3. **Pack 匹配（假设检验式，不是先分类再找）**：
   - Pack 位置：`packs/` 目录（与本 SKILL.md 同级；仓库安装时为 `<仓库>/skills/fomor/packs/`），每个 `.md` 文件是一个 Pack；
   - **逐个**阅读已安装的 Pack：先假设「当前用户活动符合该 Pack 覆盖的领域」，再按 Pack 的适用范围核对用户实际情况——不符合就否定假设、跳过，符合就列入本次适用；
   - 一个用户可能同时涉及多个领域，可匹配多个 Pack；也可能所有 Pack 都不适用；
   - 记录：已安装的 Pack、匹配成功的、不适用的及原因——Step 3 输出要用。

### Step 2：专项探索与搜索（Exploration & Search）

#### 2.1 根据 Pack 确定探索方向

1. 阅读所有匹配成功的 Pack，遵循其中的观察方向、判断规则、探索方法和筛选标准。
2. 结合用户提问、必要上下文、项目情况和 Agent 已提供的内容，识别值得进一步探索的方向。Pack 提供的是探索边界与启发，不是要求逐项完成的清单；不要为了覆盖所有类别而凑内容。
3. 一个活动可以匹配多个 Pack。分别按对应 Pack 的要求形成探索方向，不把其他领域 Pack 的规则套用过来。
4. 没有匹配的 Pack 时，不自行发明专业领域的探索流程。仍可基于已有信息分析用户行为背后的可能原因，但不要直接回答用户原问题，也不要把通用分析包装成专业领域探索；将可能涉及的领域及 Pack 建议融入报告开头。

#### 2.2 广泛搜索

根据探索方向寻找用户可能尚未接触、但与其行为或目标确实相关的内容。搜索不以深入研究某一个主题为目标，而是尽可能发现有价值的不同方向。

重点关注以下内容，具体搜索范围由探索方向决定，不要求每类都有发现：

- **知识**：专业概念、术语、技术原理、设计理念及相关理论。
- **工具**：工具、技术、开源项目及其能力。
- **方法论**：成熟的工作方法、实践流程和解决问题的思路。
- **资源**：真实案例、优秀作品、教程、文档、社区及其他参考资料。

不要只搜索用户已经提到的内容，也要主动寻找相关但用户可能尚未了解的方向。按主题选择合适的搜索来源，优先寻找能够直接说明内容本身的资料。

#### 2.3 核实与筛选

搜索结果必须经过必要核实，不能仅凭标题或摘要就作为发现写入报告。

- 确认工具、技术、项目或资源真实存在，相关描述与其实际能力相符。
- 优先使用官方文档、项目仓库、真实案例和可信的专业资料；必要时交叉核对关键事实。
- 关注内容是否与用户的具体行为或目标相关，是否能带来新的认知或实现可能。
- 排除重复、过时、缺乏依据、关联较弱或只有名称而没有实际价值的内容。
- 区分已核实的事实与经验性观点；无法确认的内容不作为确定结论输出。

搜索遵循三个要求：**广泛、真实、精准**。不追求把少数主题研究透彻，而是让用户接触到更多可靠且真正相关的方向。每个方向只需掌握足以准确介绍它、说明其价值并提供可靠入口的信息。

排除以下内容：

- 用户已经明确意识到、正在主动探索的内容，除非能提供明显不同的新视角；
- Agent 已经充分解释过且没有新增价值的内容（但不因此认定用户已经掌握）；
- `dislikes` 中记录的内容；
- 近期报告已经探索且没有新进展的主题。可粗读 `~/.fomor/reports/` 近期报告进行语义层面的判重；历史报告只用于判重，不作为用户背景或项目状态输入。

### Step 3：输出（Output）

报告风格：简洁、直接、结构化但有人性化。报告的目的不是替用户完成学习，而是让用户快速发现值得了解的新知识、新工具、新方法和新资源，并能自行选择感兴趣的方向。不要写成长篇研究报告，不需要通过场景、提问或共鸣引入内容。

报告写入 `~/.fomor/reports/<YYYY-MM-DD>.md`，并完整展示在对话里。最终格式严格遵循以下结构：

```markdown
# Fomor 探索报告

近期你主要在……（简短说明用户正在做什么、围绕内容进行了怎样的分析或尝试，并在同一个段落中说明匹配到的探索包及其大致范围；如果没有匹配，或匹配结果无法明确说明，则简要指出可能涉及的领域、当前覆盖情况，以及是否建议设计该领域的探索包。）
```

格式要求：

1. **报告开头**：只写一个简短段落，不再拆分小节。用自然、完整的句子说明用户近期在做什么、进行了怎样的探索、匹配到了哪些 Pack；若没有匹配或无法明确判断，也在同一段中说明可能涉及的领域、覆盖缺口及 Pack 建议。不要另设 Pack 匹配情况或未覆盖领域章节。
2. **领域目录**：开头段落之后直接列出匹配到的领域锚点，不增加「探索目录」等标题。每个标题先写清探索包领域，括号中概括本次实际涉及的知识、工具、资源或方法论，有什么写什么。点击后跳转到对应领域页面。
3. **领域页面目录**：进入领域页面后，先列出四类内容的锚点目录，顺序为知识、工具、方法论、资源。每一类使用一个锚点标题，标题中将该类别下具体的专业名词、知识名称、工具名称、方法或资源名称连成一句话，名称之间用顿号分隔。**不要把这些名称改写成「知识点一」等占位词，也不要用无序列表逐项列出。** 整句链接跳转到该类别的内容区域。
4. **具体内容**：再按知识、工具、方法论、资源展开。每项以具体名称为标题，用简短文字介绍内容，并说明基于用户哪些提问或行为判断它可能值得了解，附上能够直接访问的可靠链接。不要写成长篇教程或深度研究。
5. **内容取舍**：四类内容不要求全部出现；没有有价值的发现就省略该类，不要为了填满结构而凑数。目录只列出实际有内容的类别和条目。可以有多个领域页面，每个领域页面都使用相同结构。
6. **锚点**：目录链接必须与对应标题的实际锚点一致。类别目录链接到对应的二级标题，例如 `[CSS Compositing、CSS Masking](#知识)` 对应 `## 知识`。领域目录链接到对应领域标题。生成后检查锚点能否正确跳转；不同领域或重复标题可能产生冲突时，使用唯一标题或明确的锚点后缀。
7. **没有匹配领域**：不生成虚构的领域页面或空目录。把可能涉及的领域、未覆盖原因和 Pack 建议写在开头段落中；如果有其他领域匹配成功，则照常展示已匹配领域的目录。

报告完整生成并展示成功后，才执行提交——把 Step 0 的 `snapshot` 原样传回：

```bash
printf '%s' '{"snapshot":{...Step 0 的 snapshot 原文...}}' | scripts/fomor finish
```

`finish` 只删除本轮已读取的事件（分析期间新增的消息保留到下一轮）；`finish` 报错时不要重试删除，如实报告——事件留在磁盘上，下次重新分析。分析失败则根本不调用 `finish`。

#### Pack 文件格式

每个 Pack 是一个 Markdown 文件（`packs/<领域名>.md`），至少包含以下小节：

```markdown
# <Pack 名称>

覆盖领域：一句话说明这个 Pack 覆盖什么专业领域。
适用范围：什么情况下「用户活动符合本领域」的假设成立；什么情况应否定假设。

## 观察方向
（在本领域中，用户的哪些提问/行为值得注意）

## 判断规则
（如何判断用户可能缺什么：概念、术语、方法、工具、视野……）

## 探索方法
（按什么步骤、用什么角度去寻找新知识/方法/方案）

## 筛选标准
（什么样的发现值得推荐，什么应排除）
```

Pack 由用户与团队维护；主动调用时可以按 Step 3 的建议协助起草并放入 `packs/`，每日自动化任务不得创建或修改 Pack。

## C. 用户主动调用（唯一允许更新 Disliked 的入口）

用户主动调用 Fomor Skill 时可以：

- **手动执行一次探索**：按 B 部分 Step 0→3 执行；
- **查看/讨论结果**：读 `~/.fomor/reports/` 下当天的探索结果，展开讨论；
- **更新 Disliked**：仅当用户**明确表达拒绝**时执行：

```bash
scripts/fomor dislike --name "<内容名称>" [--category content_preference]
```

Disliked 更新规则：

1. 只记录用户明确说「不想再看到这类内容」的条目；
2. 用户只是调用了 Skill 但没表达拒绝 → **不更新**；
3. 用户沉默、没点击、没追问、没用某个方案 → **不推断为拒绝**；
4. 重复条目自动去重，不需要反馈状态或时间线。

## 数据与配置速查

```text
~/.fomor/
├── config.json               {"timezone": "Asia/Shanghai", "schedule": "03:00"}
├── events/YYYY-MM-DD.jsonl   用户问题，无处理标记；finish 按快照清理已分析的
├── profile.json              {"version": 1, "dislikes": [...]} 只记明确拒绝
├── reports/                  当天的探索结果（留存，可随时删除，仅用于判重）
└── runtime/state.json        {"last_successful_analysis_at"}
```

Event 只有 5 个字段：`event_id`、`session_id`、`timestamp`、`user_message`、`fingerprint`。

Pack 目录：`packs/`（与本 SKILL.md 同级），每个 `.md` 文件一个领域 Pack，格式见 B 部分「Pack 文件格式」。

常用命令：`scripts/fomor status`（概览）、`cat ~/.fomor/reports/*.md`（查看结果）。
