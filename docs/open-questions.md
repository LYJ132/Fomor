## 二、P0：开始搭建前必须确认

### Q1. 首个适配的 Agent 平台与 Hook 能力

- **现状**：PRD 定位是「适配 Trae 的插件」，但 MVP 要求「首个平台需支持用户发送消息后执行 Hook」。
- **待确认**：
  1. Trae 是否提供可用的 UserMessage / Prompt 提交 Hook？安装与注册方式是什么？
  2. 若暂不可用，是否先用「平台无关的采集接口 + 手动/文件导入」跑通链路？
  3. 是否具备按 `session_id` 读取历史会话的能力？
- **建议**：定义 `Collector` 抽象接口，先实现一个具体适配器；若 Trae Hook 暂不可用，则先实现 `file-import` / `manual` 采集器，保证核心链路可验证。
- **风险**：这是唯一「外部依赖不确定」的 P0 项，建议先用可替代方案解耦。

### Q2. MVP 技术栈

- **候选**：Python 3.11+ / TypeScript(Node) / Go
- **建议**：Python 3.11+。原因：LLM 编排、文本处理、JSON 存储、后续接搜索/论文生态成本最低；单机后台服务足够。
- **待确认**：是否有既定团队技术栈偏好。

### Q3. 后台运行与部署形态

- **现状**：已确定是「独立后台服务」，但运行环境未定。
- **待确认**：本地常驻进程 / 定时任务（cron）/ Docker / 远程运行。
- **建议**：MVP 用「单进程 + 内置调度器（APScheduler 或自研 tick）」，同时支持 `run-once` 命令便于调试；预留 Dockerfile。
- **说明**：Hook 必须轻量，只写事件，不做分析（PRD 6.1.2、12.1）。

### Q4. 模型与搜索 Provider

- **待确认**：
  1. 用哪个 LLM（OpenAI / Anthropic / DeepSeek / 本地模型）？
  2. 搜索来源（GitHub、网页搜索、论文、社区）以及是否自建搜索。
- **建议**：
  - LLM 统一走 **OpenAI 兼容协议**（`base_url` + `api_key` + `model` 可配），一套代码兼容多数供应商。
  - 搜索做成 `SearchProvider` 接口，MVP 先接 1 个（如通用 Web 搜索），其余留空实现。
  - 不在 MVP 自研搜索引擎（PRD 9.4）。

### Q5. 结果交付形态

- **现状**：PRD 提到独立 APP 模板 或 IM 渠道，均未定稿。
- **建议**：MVP 先做 **CLI 生成 + 本地静态 HTML 查看**，把 `DeliveryRuntime` 抽象好；IM（如飞书）作为后续渠道接入。

## 三、P1：MVP 内需给出默认值

### Q6. Event 保留期限
- PRD 倾向 48 小时。建议：默认 48h，可在 `settings.json` 配置；清理只删 Event，不影响 Topic。

### Q7. 问题聚合策略
- 建议：按自然日 + 滑动时间窗收集 Event → 先关键词/嵌入粗聚类 → 再让 LLM 在候选簇内判断是否属于同一探索主题 → 允许跨 Session、跨项目。
- 明确：不依赖固定意图分类；证据不足时保留多个假设。

### Q8. 探索机会评分
- 维度（PRD 6.3.2）：解决空间、潜在收益、认知增量、适用性、探索必要性。
- 建议：每维 0–5 分；先设硬性过滤（如「当前方案已足够好」直接不探索）；最终输出「值得探索 / 暂时观察 / 无探索价值」三档，而非单一分数。

### Q9. 去重与重复推荐
- 建议：`event_id` 幂等写入；Discovery 记录已介绍方案的指纹（名称+核心机制哈希）；生成前比对 Topic 历史，跳过用户已明确了解的内容。

### Q10. Topic 生命周期
- 建议：默认 30 天无活动 → Dormant；90 天 → 评估归档；用户明确拒绝才记负向偏好；沉默视为未知。

### Q11. 数据脱敏
- 建议：外部模型调用前做规则脱敏（API Key、绝对路径、邮箱、内网 IP、连接串）；保留开关与日志；原件仅本地保存。

## 四、P2：可延后

- **Q12 用户认知画像**：MVP 只记录用户显式反馈（了解/感兴趣/不相关/用过），不做推断。
- **Q13 方案成熟度/证据质量**：MVP 用结构化字段（证据来源、可访问链接、限制说明），不做自动打分。
- **Q14 交付形态最终选择**：MVP 仅 HTML，APP/IM 后续评估。
- **Q15 反馈交互**：MVP 在 HTML/CLI 提供固定选项，足够验证记忆闭环。
- **Q16 多平台适配**：MVP 只做 1 个平台，但适配层接口先定好。

## 五、建议的 MVP 技术方案（供确认）

| 模块 | 建议实现 |
|---|---|
| 语言 | Python 3.11+ |
| 存储 | 本地 JSON（按 PRD 9.3 目录结构），原子写入 + 文件锁 |
| 调度 | 单进程内置调度器 + `run-once` 调试命令 |
| 采集 | `Collector` 接口 + 首个适配器（Trae Hook 或文件导入） |
| 分析 | LLM（OpenAI 兼容）完成聚合、问题理解、评分、方案生成 |
| 搜索 | `SearchProvider` 接口，MVP 接 1 个实现 |
| 交付 | CLI + 静态 HTML 报告 |
| 验证 | 用 PRD 第十六章三个案例做端到端样例 |

**MVP 第一条可跑通的链路**：
`事件写入 → 聚合 → Problem Understanding → 探索评分 → 生成探索方向 → 搜索/验证 → Discovery JSON → HTML`
